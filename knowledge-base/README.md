# knowledge-base：售后制度与客服手册

本目录存放 MCPGate 售后场景的三份知识库文档、知识库清单与索引配置、检索探针，以及离线校验、同步导入与检索验证脚本。

## 目录结构

```
knowledge-base/
├── README.md                     # 写作规范、条款设计表与操作步骤
├── kb.yaml                       # 知识库清单与索引、检索参数
├── probes.yaml                   # 检索探针（问题 -> 期望命中的条款）
├── .env.example                  # KB_ 前缀环境变量样例
├── pyproject.toml                # 脚本与测试依赖（Python 3.12）
├── uv.lock
├── docs/
│   ├── policy/售后制度.md        # 知识库「售后制度」（policy），35 条
│   └── handbook/
│       ├── 客服操作手册.md       # 知识库「客服手册」（handbook），18 条
│       └── 故障排查手册.md       # 知识库「客服手册」（handbook），12 条
├── scripts/
│   ├── lint.py                   # W1–W12 规则与 W13 废止条款识别、编号/引用离线检查脚本
│   ├── sync.py                   # 建库、上传/更新与不可用文档自愈、轮询索引、核对分段、写出 kb.lock.json
│   └── probe.py                  # 执行检索探针并验证召回
└── tests/
    └── test_kb.py                # lint / sync / probe 单元测试
```

两座知识库的划分原则：
- `policy`（`售后制度`）：订单售后咨询与提交退款两条路径只检索本库，确保检索名额不被操作步骤与故障排查占用。
- `handbook`（`客服手册`）：制度与操作咨询路径同时检索 `policy` 与 `handbook`。能否退款只以《售后制度》为准，另两份文档仅说明操作方法与故障认定方法。

## 写作规范摘要（W1–W13）

规范对应 Dify `MarkdownExtractor` 与自定义分段规则，目标是「一条条款恰好成为一个分段，且分段首行自带文档名与条款编号」：

| 规则 | 要求 |
|---|---|
| W1 | 文件为无 BOM 的 UTF-8 `.md`，通过文件上传接口导入 |
| W2 | 恰好一个一级标题 `# <文档名>`，紧接一两句文档用途与效力说明（成为独立分段） |
| W3 | 其余标题仅用二级标题，格式固定为 `## <文档名> 第 <章>.<条> 条 <条款标题>`，文档名与一级标题一致 |
| W4 | 不使用三级及以下标题；「章」只体现在编号第一段数字中 |
| W5 | 标题中文档名与条款标题不加书名号，标题与正文行首不以 Dify 会裁剪的标点开头 |
| W6 | 条款内部与一级标题说明内部不留空行；相邻分段之间恰好空一行 |
| W7 | 每个分段（含标题与正文）不超过 600 字，避免超过 `max_tokens: 1000` 被二次切分 |
| W8 | 禁止 `<`、`>`、HTML、Markdown 表格、图片 `![`、链接 `](`；比较关系一律写成文字 |
| W9 | 一般条款正文每行以固定标签开头：`适用：`、`规则：`、`处理：`、`例外：`（无则省）；《故障排查手册》第 1–3 章排查条目使用 `现象：`、`排查：`、`认定：` |
| W10 | 涉及方案 1.5.3 / 1.5.4 / 1.10 / 3.6.2 的英文枚举值与业务字段名时，必须紧跟对应中文并用全角括号包住（如 `质量问题（quality_issue）`、`退货退款（return_refund）`、`已签收天数（days_since_delivery）`）；`lint.py` 对全角与半角括号内未登记英文记号报错（半角括号同时提示改用全角括号），仅放行最小化系统错误码白名单与符合 1.5 / 3.6.1 编号规则的示例单号（如 `A1023`、`B2087`、`C3051`、`C0001`、`T5001`、`AP000001`、`R000101`）；不带括号的普通英文词（如 `HTTP`、`SKU`、`VIP 客户`）不检查 |
| W11 | 条款正文出现「N 天 / N 日」且同句含「超过 / 超出 / 不超过 / 达到 / 以内 / 之内 / 内 / 后 / 不满 / 满」等期限措辞时，同句必须包含「已签收天数」或「已发货天数」，并带与期限数字一致的明确边界说明（如「含第 N 天」「不含第 N 天」「N 天及以上」；「日」视同「天」） |
| W12 | 跨条引用一律使用明确编号 `第 X.Y 条` 或 `《文档名》第 X.Y 条`，禁止「上一条」「如前所述」等相对引用 |
| W13 | 条款编号稳定，发布后不重排、不复用；废止条款保留编号并将正文改为 `本条已废止`，新增条款追加在章末（说明：跨版本编号稳定性靠评审保证，`lint.py` 仅机械识别「本条已废止」条款并校验单次文档内编号唯一且严格递增） |

## 文档大纲与条款设计表

### 1. 《售后制度》（`docs/policy/售后制度.md`，35 条）

| 编号 | 标题 | 规则要点 |
|---|---|---|
| 1.1 | 适用范围与效力 | 适用于全部区域订单；能否退款仅以本制度为准，另两份手册仅说明操作与排查方法 |
| 1.2 | 术语与系统字段 | 已签收天数（`days_since_delivery`）按自然日计（签收当天为第 0 天）；列出类目、原因类别、申请类型、客户等级、订单状态中英文取值 |
| 1.3 | 判定顺序 | 订单状态与金额（第 5 章）→ 特殊类目（第 4 章）→ 原因类别（第 3 章）→ 无理由与会员（第 2、6 章）；特殊规定优先于一般规定 |
| 1.4 | 事实依据 | 以订单系统实时记录为准；期限按受理时已签收天数计算；原因优先取待处理（`open`）工单，无工单取客户陈述并注明 |
| 1.5 | 制度未覆盖的情形 | 不得自行处理，请示负责该区域的主管 |
| 2.1 | 七天无理由退货 | 无理由（`no_reason`）、一般类目、已签收天数不超过 7 天（含第 7 天）可退货退款（`return_refund`）；类目限制见第 4 章，会员扩展期见第 6.1 条 |
| 2.2 | 超过无理由期 | 普通客户达到 8 天及以上（会员达到 16 天及以上）的无理由申请不予受理 |
| 2.3 | 商品状态要求 | 无理由退货商品须完好、配件齐全、不影响二次销售，由客服向客户核实 |
| 2.4 | 无理由的处理方式 | 已签收订单无理由只支持退货退款（`return_refund`），不支持仅退款（`refund_only`） |
| 3.1 | 质量问题的认定 | 功能故障、性能不达标、做工缺陷属质量问题（`quality_issue`）；人为损坏与正常磨损不属于；方法见《故障排查手册》 |
| 3.2 | 质量问题退货期限 | 数码家电、服饰鞋包、家居日用、定制商品的质量问题，已签收不超过 30 天（含第 30 天）可退货退款，运费由商家承担 |
| 3.3 | 质量问题超过三十天 | 已签收达到 31 天及以上的质量问题不支持退货退款，引导保修维修 |
| 3.4 | 发错货 | 发错货（`wrong_item`，含定制内容不符）已签收不超过 15 天（含第 15 天）可退货退款，运费由商家承担 |
| 3.5 | 运输破损 | 运输破损（`damaged_in_transit`）已签收不超过 7 天（含第 7 天）可退货退款或仅退款，运费由商家承担；生鲜按第 4.1 条 |
| 3.6 | 未收到货 | 已发货未签收（`shipped`）且已发货达到 7 天及以上（含第 7 天）可全额仅退款；不满 7 天先跟进物流 |
| 3.7 | 原因为其他 | 原因为其他（`other`）不直接适用本章各条，按第 1.5 条请示主管 |
| 4.1 | 生鲜食品 | 生鲜食品（`fresh_food`）不支持无理由退货；质量问题或运输破损须在已签收不超过 2 天（含第 2 天）内提出，仅退款无需退回；超期不受理 |
| 4.2 | 定制商品 | 定制商品（`custom_made`）不支持无理由退货；质量问题按第 3.2/3.3 条，发错货按第 3.4 条 |
| 4.3 | 其他类目 | 数码家电（`electronics`）、服饰鞋包（`clothing`）、家居日用（`home`）适用一般规定 |
| 5.1 | 可退款的订单状态 | `paid` / `shipped` / `delivered` / `completed` 可进入退款判断；`pending_payment` / `cancelled` 没有可退款项 |
| 5.2 | 未发货订单 | 已支付未发货（`paid`）可全额仅退款（`refund_only`），不限原因与类目 |
| 5.3 | 退款金额 | 必须大于 0 且不超过 `refundable_amount`；默认取工单申请金额，无则取可退金额全额；部分退款须注明范围 |
| 5.4 | 不得重复退款 | 已有 `processing` 退款单、已全额退款（`full`）或已有 `pending` / `executing` 审批申请时不得重复提交 |
| 5.5 | 运费承担 | 无理由退货由客户承担运费；质量问题、发错货、运输破损、未收到货由商家承担 |
| 6.1 | 会员无理由期 | 会员（`vip`）无理由退货期限为已签收不超过 15 天（含第 15 天） |
| 6.2 | 会员权益的边界 | 不改变第 4 章类目限制，不延长第 3 章及生鲜期限，无理由退货运费仍由客户承担 |
| 7.1 | 退款须经审批 | 所有退款均通过售后助手提交审批，负责该区域的主管审批同意后才执行 |
| 7.2 | 审批回避 | 主管不得审批本人提交的退款申请 |
| 7.3 | 大额退款 | 单笔达到 2000 元及以上属大额退款，须写明核实事实并由主管重点复核 |
| 7.4 | 审批时效 | 申请提交后 72 小时未审批自动过期（`expired`），需重新提交 |
| 7.5 | 不符合制度的申请 | 不符合制度的退款不得通过助手提交；客户坚持的报主管线下处理 |
| 7.6 | 数据范围 | 客服与主管只处理本人负责区域订单，跨区域转交对应区域同事 |
| 8.1 | 已驳回的工单 | 同一诉求不重复受理；有新事实时按新申请判断 |
| 8.2 | 没有售后工单的订单 | 先向客户确认诉求与原因，再按相应条款判断并在说明中注明 |
| 8.3 | 多类目订单 | 按各商品类目分别判断，部分可退时按第 5.3 条办理部分退款 |

## 环境变量说明（`.env`）

复制 `.env.example` 为 `.env` 后填写（`.env` 与 `kb.lock.json` 均为本地产物，不入库）：

| 变量 | 默认值 | 说明 |
|---|---|---|
| `KB_DIFY_BASE_URL` | `http://localhost:8088` | Dify 入口地址（不含 `/v1`） |
| `KB_DIFY_API_KEY` | 无（必填） | Dify 工作区级知识库 API Key（形如 `dataset-...`） |
| `KB_EMBEDDING_PROVIDER` | 空 | Embedding 模型供应商标识（与 `KB_EMBEDDING_MODEL` 同时填写或同时留空；留空使用 Dify 默认模型） |
| `KB_EMBEDDING_MODEL` | 空 | Embedding 模型名称 |
| `KB_RERANK_PROVIDER` | 空 | Rerank 模型供应商标识（启用重排时必填） |
| `KB_RERANK_MODEL` | 空 | Rerank 模型名称；非空时 `sync.py` 与 `probe.py` 自动开启 `reranking_enable: true`、`reranking_mode: reranking_model` 并将 `top_k` 设为 `6` |

## 检索探针格式（`probes.yaml`）

`probes.yaml` 顶层包含 `probes` 列表，每条探针结构如下：

```yaml
probes:
  - id: P01
    dataset: policy        # 对应 kb.yaml 中的 dataset key（policy 或 handbook）
    query: 数码家电 质量问题 退货退款 已签收 18 天 普通客户
    expect:                # 期望在前 top_k 个检索分段中全部命中的条款列表
      - 售后制度 第 3.2 条
      - 售后制度 第 2.2 条
      - 售后制度 第 5.5 条
```

`probe.py` 按每个返回分段 `segment.content` 的首行提取 `<文档名> 第 X.Y 条` 并与 `expect` 逐项比对，全部命中退出 `0`，任意缺失退出 `1`。

## 同步导入说明（`sync.py`）

- **远端状态读取与同名自愈**：列出远端文档时读取 `display_status`、`indexing_status`、`enabled`、`archived`。同名文档有多份时优先保留可用（`available`）的一份、其余先删除；可用文档走 `update-by-file`；出错（`error`）、已禁用（`disabled` / `enabled=false`）、已归档（`archived` / `archived=true`）或暂停（`paused`）文档先删除再 `create-by-file`（已归档文档遇到 403 时自动先 `un_archive` 再删除）；索引中（`indexing` / `queuing` / `waiting` / `parsing` / `cleaning` / `splitting`）先等待其进入终态再按最终状态走更新或删后重建。
- **不可用回退**：若 `update-by-file` 仍返回不可用类错误（如 400 `Document is not available`），自动回退执行一次「删除后 `create-by-file`」，仍失败则报错退出并在错误信息中写明文档名与远端状态。
- **等待超时口径**：**等待既有索引中文档结束、本次上传/更新后的 `indexing-status` 轮询各自单文档上限 5 分钟**（默认 `--poll-timeout 300`），任一阶段超时即失败退出。

## 常用命令

在 `knowledge-base/` 目录下执行：

```bash
# 1. 安装脚本与测试依赖
uv sync

# 2. 离线检查三份文档与探针一致性（W1–W12 及 W13 废止条款识别）
uv run python scripts/lint.py

# 3. 同步导入 Dify 知识库并生成 kb.lock.json（需先配置 .env 且 Dify 运行中）
uv run python scripts/sync.py

# 4. 执行检索探针验证召回（需先完成 sync.py）
uv run python scripts/probe.py

# 5. 运行单元测试与代码规范检查
uv run pytest -v
uv run ruff check . && uv run ruff format --check .
```

修订制度条款的标准流程：修改 `docs/**/*.md` → `lint.py` → `sync.py` → `probe.py`。
